# ADR 007 — Конструктор базы и настройка исходного предмета

Статус: принято (v0.4, 2026-10-02)

## Контекст

До v0.4 исходный предмет создавался в основном импортом текста Ctrl+C; «пустая база» была списком
из двух названий без картинок и свойств. Нужен ручной путь, как в Craft of Exile: выбрать класс и
базу, увидеть её, задать item level, качество, сокеты, стартовые моды и fractured — и только потом
крафтить. При этом нельзя смешать настройку стартового предмета с крафтом, а данные, которые движок
не моделирует (качество, сокеты), не должны тайком влиять на проценты.

## Решение

1. **Определение базы ≠ состояние предмета.** `ItemBase` (craft-domain) расширен необязательными
   полями: `artAssetId` (id игрового арта), `details` (свойства, требования, implicit-строки — только
   для показа, со своим `provenance`) и `setup` (`ItemSetupRules`: диапазон качества, допустимые
   количества слотов по видам). `ItemState` по-прежнему ссылается на базу только через `baseId` и
   ничего из определения не копирует.
2. **ItemState получил `quality: number | null` и `slots: ItemSlotState[]`.** Это записанные факты
   о предмете (из ручной настройки или из строк `Quality:` / `Sockets:` при импорте). Ни один движок
   их не читает, пока нет проверенного правила (инвариант 37, тест в `item-setup.test.ts`).
3. **Слоты — общая инфраструктура, а не правило PoE 2.** Вид слота — строка из данных
   (`'rune-socket'`), допустимые количества — `SlotRule.options` конкретной базы. Свойство без правила
   у базы не предлагается вовсе (инвариант 40).
4. **Настройка исходного — отдельный модуль `craft-session/item-setup.ts`:** `createItemFromBase`,
   `setItemLevel`, `setQuality`, `setSlotCount`, `setSourceModifierFractured`, `itemSetupFields`,
   `sourceTierOptions`, `sourceModifierIssues`. Это не действия крафта: они меняют только source, не
   пишут шагов, ничего не стоят. Некорректный ввод возвращает предмет без изменений.
5. **Fractured при настройке ≠ Fracturing Orb.** `setSourceModifierFractured` описывает «на моей базе
   этот мод уже fractured». Настоящая механика Fracturing Orb появится позже как отдельный
   `CraftAction` со своим `effect.kind`, правилами и ценой (инвариант 36).
6. **Выбор тира при правке исходного — через общий пул.** `sourceTierOptions` строит тот же
   manual-edit пул, что и обозреватель в режиме замены, поэтому выпадающий список и пул не расходятся
   (закрывает P2-06 аудита). `sourceModifierIssues` помечает, но не удаляет моды, которые после смены
   ilvl или базы стоять на предмете уже не могут.
7. **Арт — не зависимость домена.** Домен хранит только `artAssetId`. Где лежит картинка, знает сайт:
   `apps/web/src/lib/art-manifest.ts` (файл, размер, источник, адрес на CDN для атрибуции). Файлы
   скачаны один раз и раздаются сайтом из `public/icons/game`; хотлинка нет (тест `tests/icons.test.ts`).
8. **Каталог баз отделён от модов.** `craft-db/src/fixtures/bases.ts` — 13 реальных баз трёх классов:
   названия из `trade2/data/items`, свойства/требования/implicit/арт из JSON обычных (normal) предметов
   на официальном трейде (`official.trade2-listings`, kind `observation`). Теги спавна и правила
   setup — fixture / experimental. Полный BaseDB заменит этот файл данными той же формы; селектор
   читает каталог через `CraftDbView.listBases()` / `listItemClasses()` и не меняется.
9. **Клик инструментом — функция ядра `applyToolStep`:** инструмент → действие из данных → цена
   попытки → `applyStep`. Нет инструмента или нет модели — отказ с причиной, сессия та же.
   Курсор с валютой — чисто визуальный оверлей сайта (`pointer-events: none`, `aria-hidden`), сам
   ничего не применяет (инвариант 43).
10. **Цель на другой базе не планируется.** `targetBaseCheck(source, target)`: при `mismatch` сайт
    показывает предупреждение, а цели шага из такого target не строятся (инвариант 41).
11. **Fractured-требование цели выполняется только fractured-модом** (статус `not-fractured`), и
    действия «добавить мод» к нему не планируются (инвариант 42; закрывает P1-09 аудита).
12. **Рассинхрон source/current считается от начала ветки**, а не от первого применённого шага:
    после «правка исходного → отмена всех шагов» Reset остаётся доступен (закрывает P1-10 аудита).

## Последствия

- Реальный BaseDB подключается заменой данных, без правок UI и домена.
- Когда появится проверенное правило качества или сокетов, оно станет отдельной функцией в пакете с
  тестом, а не формулой в JSX; до тех пор числа записываются и показываются, но в расчёт не идут.
- Fracturing, сокетирование рун, качество как крафт — будущие `CraftAction`, а не настройки.
