# ADR 005 — Craft session и демо-применение действий

Статус: принято (v0.2, 2026-10-02)

## Контекст

v0.1 считала шанс одного шага. Пользователю нужен рабочий стол: исходный предмет, текущий предмет,
который меняется после действий, целевой пример, история и потраченное. Для этого нужно
«применять» действия, хотя полного и проверенного симулятора механик PoE 2 нет.

## Решение

1. Новый пакет **`craft-session`** (зависит от craft-domain, craft-db, probability-engine, economy).
   Отдельный пакет, а не часть probability-engine: движок вероятностей остаётся чисто аналитическим
   и детерминированным, а случайность живёт только здесь.
2. **`applyAction(item, action, rng) → ApplyOutcome`** — чистая функция. Пул берётся из того же
   `buildEligiblePool`, мод выбирается пропорционально весу, значения выпадают равномерно в диапазоне
   тира с точностью, в которой записан диапазон. Результат — новый `ItemState`
   (`withExplicitModifier`), исходный не меняется.
3. **Честные отказы** вместо догадок: `pool-blocked` (предмет нельзя оценить), `no-eligible-modifiers`,
   `unknown-weights` (вес неизвестен — разыгрывать нельзя, инвариант 8). Предмет и сессия при отказе
   не меняются, затраты не записываются.
4. **RNG передаётся явно.** Сессия хранит `seed` и счётчик бросков `rollCount`; бросок n использует
   поток `rollRng(seed, n)`. Сессия воспроизводима, а отмена и повтор шага не дают тот же результат
   (счётчик не уменьшается). Источник seed (crypto) находится на стороне сайта, а не в ядре.
5. **`CraftSession`** — неизменяемое значение: `source`, `current`, `target` (три разных предмета),
   `steps[]`, `seed`, `rollCount`, `gameVersion`. Операции: `createSession`, `startFromSource`,
   `withTarget`, `applyStep`, `undoLastStep`, `sessionSpent`.
6. **Потрачено = сумма записанных шагов.** Шаг хранит `AttemptCost` на момент применения, поэтому
   поздняя правка цен не переписывает историю. Ожидаемая стоимость этапа считается отдельно
   (economy) и в UI визуально отделена от факта.
7. **Сравнение с целевым предметом** (`compareToTarget`): сопоставление по группе мода и стороне,
   тир 1 — лучший; статусы matched / better-tier / worse-tier / missing / unknown, плюс лишние моды.
   Недостающие моды целевого предмета становятся целями шага (`targetFromModifier`: этот тир или лучше).
8. **Обозреватель пула** (`explorePool`) — в probability-engine, так как это представление того же пула:
   вкладки (пока по стороне), группы, тиры, статусы eligible / already-present / blocked / excluded.

## Последствия

- Сайт меняет предмет только через `applyStep`; в React нет правил и случайности, кроме генерации seed.
- Симуляция помечена как демо везде: в UI (баннер, подпись под кнопкой, метка в истории) и в документации.
- Новое действие с другим `CraftEffect.kind` потребует ветки в `applyAction`. `switch` по `kind`
  не даст молча применить к нему модель «добавить мод».
- Пока поддерживается только добавление мода. Удаление, замена, Omen как отдельный слой, Essence
  и Desecration — следующие этапы, и каждый требует подтверждённых данных о механике.
