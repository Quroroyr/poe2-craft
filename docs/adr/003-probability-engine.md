# ADR 003 — Probability Engine

Статус: принято (v0.1, 2026-10-02)

## Контекст

Нужен прозрачный расчёт шанса одного этапа: не чёрный ящик, а число, которое можно объяснить
по шагам и проверить руками.

## Решение

1. **Пул строится по всем модам версии**, каждый получает список причин исключения
   (`ExclusionReason`). Проверяются: spawn-вес на базе (первый подходящий тег), ilvl,
   минимальный уровень мода у действия, разрешённые стороны, свободные слоты,
   мод уже на предмете, занятые группы (включая fractured и выведенные из нераспознанных строк).
   Мод доступен ⇔ причин нет.
2. **Вероятность**: `P = Σ вес допустимых тиров цели / Σ вес доступных модов`.
   Ожидаемое число попыток `1/P`. Шанс за N попыток `1 − (1 − P)^N` (через `expm1/log1p`).
   Квантиль попыток — наименьшее `n` с `1 − (1 − P)^n ≥ q`, считается аналитически,
   с защитой от ошибок округления.
3. **Неизвестные веса** не подменяются: неизвестен вес конкурента → `bound: 'upper-bound'`,
   неизвестен вес цели → `indeterminate`.
4. **Статусы вместо исключений**: `blocked` (предмет нельзя оценить), `already-satisfied`,
   `target-unavailable` (с причинами по каждому тиру), `indeterminate`, `ok`.
5. **Объяснение** — `ExplanationStep[]`: данные, а не текст. Язык и формулировки на стороне UI.
6. **Достоверность результата** — слабейший `confidence` среди данных, от которых он зависит.

## Предположения, требующие проверки для PoE 2

- Модель «добавить один мод, выбранный пропорционально spawn-весу среди доступных» (Exalted Orb).
- Правило «первый совпавший тег базы определяет вес».
- Один мод с несколькими группами блокирует все свои группы.

Они записаны как experimental и проверяются по данным игры до production-набора.

## Последствия

- Движок детерминирован и синхронен, поэтому тесты точные (без допусков на симуляцию).
- Модель repeat-until-success подходит для одного повторяемого этапа. Для этапов с откатом
  (recovery) и ветвлением нужен симулятор или марковская модель — это следующий этап.
