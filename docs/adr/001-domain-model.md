# ADR 001 — Доменная модель: правила, а не рецепты

Статус: принято (v0.1, 2026-10-02)

## Контекст

Цель продукта — автоматический поиск маршрута крафта. Если хранить готовые рецепты
(«для +4 Projectile сделай A → B → C»), каждый патч ломает их вручную, а новые цели требуют новых
рецептов. Солверу нужны правила, из которых маршрут выводится.

## Решение

- Храним **правила**: `ModifierDefinition` (один тир = одна запись), `ModifierGroup`,
  `ItemBase` с тегами, `CraftAction` с `CraftEffect`, `AffixLimitRule`.
- `ItemState` — неизменяемое значение: stable id модов + выпавшие значения + флаг fractured.
  Определения в состояние не копируются.
- Действие описывается данными (`effect: { kind, ... }`), а исполняет его код движка по `kind`.
  `CraftEffect` — discriminated union; новая механика = новый `kind`, старые не трогаются.
- Цель (`CraftTarget`) — множество допустимых id модов. Условия вида «тир 2 и выше» —
  это список тиров, без отдельной логики.
- Нераспознанные строки — часть состояния (`UnresolvedModifier`) с подсказками стороны и группы.

## Последствия

- Обновление патча = новые данные; состояния предметов остаются валидными.
- Солвер (будущий) работает с `ItemState → CraftAction → распределение ItemState`. Задел —
  `ProbabilityOk.outcomes`.
- Одно действие с несколькими эффектами (Omen + валюта) придётся выразить композицией эффектов.
  Сейчас это не реализовано: v0.1 моделирует ограничение стороны как отдельное действие.
- `ModifierTier` и `CraftStep` отдельными типами не введены (см. domain-model.md).
